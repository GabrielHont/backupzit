REST API

Integrate BackupZit with RMM platforms, monitoring (PRTG, Zabbix, Nagios, Uptime Kuma …) and your own scripts.

Tokens

Create a token under My account → API tokens. Give it the lowest role that is enough — Viewer for monitoring, Restore operator to also start backups and restore tests. The token is shown once; send it in every request:

Authorization: Bearer bzt_...

Tokens can expire, can be revoked by their owner or an administrator (Users), and stop working when the owner is disabled. Actions done with a token appear in the audit log with the token's name.

Endpoints

Responses are JSON except file downloads and Prometheus metrics. Public installer downloads are the only endpoint below that does not require a Bearer token. Base URL: https://<console>:8443. Send Content-Type: application/json with JSON request bodies. The complete /api/v1/openapi.json OpenAPI 3.1 contract uses the same Bearer authentication as the API.

Provisioning without the web console

Supply the console's database URL and data directory through BACKUPZIT_DB and BACKUPZIT_DATA_DIR, then run:

backupzit-server --create-api-token portal --role admin --expires-days 30 \
  --admin-password-file /run/backupzit-admin-password

This one-shot command initializes the console if needed, creates a token for the enabled local admin, prints only bzt_... followed by a newline to stdout, and exits before starting HTTP listeners or background services. Diagnostic messages go to stderr. Capture the token directly into your secret store. The initial password file supplies one password of 8–72 bytes; it does not reset an existing account. It can be omitted when an admin already exists or the normal environment/generated-password initialization is desired. Expiry defaults to 0 (never), with a maximum of 3650 days. Roles and token validation match the web console.

Enrollment and agent limits

POST /api/v1/enrollment-tokens
{"maxUses":1,"ttlHours":24,"label":"Reception PC"}

Returns 201 with id, code (BZ1-...), expiresAt, maxUses and metadata. The code includes the enrollment secret, agent URL and certificate fingerprint; it is shown only in the creation response. Omitted values default to one use and 24 hours. Explicit maxUses:null means unlimited; TTL must be 1–8760 hours. The legacy UI tokens remain unlimited and valid for their existing duration.

The list contains only metadata, including uses and revokedAt. DELETE revokes future enrollment and preserves the token ID on already enrolled agents; it does not disconnect them. A second DELETE returns 404.

PUT /api/v1/limits
{"maxAgents":10}

Use null for no limit or 0 to prevent new enrollment. Every non-removed agent counts, including recovery media. Lowering the limit does not remove existing agents. Token consumption, agent insertion and the shared cap are checked in one transaction, including simultaneous enrollment with different tokens. A failed enrollment consumes no use. The enrollment protocol returns an English error when the cap is reached.

Install an agent without a console session

The portal reads GET /api/v1/agent-packages server-side using its Bearer token. The array contains every installed version, sorted by filename. Select the OS, architecture (amd64, arm64, 386 or arm) and package kind. Windows legacy packages have version ending in -legacy. An empty array means no installers are available. Only versioned agent MSI/DEB/RPM files are public; repository/server packages, standalone programs, recovery media, directories and symbolic links are excluded. The console does not download missing packages.

Build the download URL as public_url + "/agent/" + file, outside /api/v1. The route needs neither a UI cookie nor a Bearer token, including when web console network access is restricted. The session-only /downloads/{file} route is unchanged. Downloads include the correct media type, Content-Length, X-Content-SHA256, a SHA-256 ETag and Cache-Control: public, max-age=3600, must-revalidate. The hash is calculated from the file and cached by file identity, size and mtime. For a ranged response the SHA-256 still describes the full installer.

Substitute an actual catalog file and its sha256 into these commands, together with the configured HTTPS public URL and a one-use BZ1-... code. SHA256_FROM_AGENT_PACKAGES is a placeholder, not a digest. Use a trusted HTTPS certificate and compare the file against the digest supplied by the authenticated catalog. The portal API token stays on the portal server. Installers contain no enrollment secrets; enrollment still requires the BZ1 code.

Windows MSI (elevated PowerShell)

The installer property is ENROLLCODE, verified in packaging/windows/agent.wxs. It invokes enroll --if-not-enrolled --pending-ok --code before starting the service. The silent command is msiexec /i package.msi /qn ENROLLCODE="BZ1-...". Exit code 3010 means success with a reboot required.

$ErrorActionPreference = 'Stop'
$Console = 'https://backup.example.com:8443'
$File = 'backupzit-agent-0.47.3-x64.msi'
$ExpectedSha256 = 'SHA256_FROM_AGENT_PACKAGES'
$EnrollCode = 'BZ1-...'
if ($ExpectedSha256 -notmatch '^[0-9a-fA-F]{64}$') { throw 'Set SHA-256 from the authenticated package catalog' }
$Msi = Join-Path $env:TEMP ([Guid]::NewGuid().ToString() + '.msi')
try {
    Invoke-WebRequest -UseBasicParsing -Uri "$Console/agent/$File" -OutFile $Msi
    if ((Get-FileHash -LiteralPath $Msi -Algorithm SHA256).Hash -ne $ExpectedSha256) { throw 'Installer SHA-256 mismatch' }
    $MsiArgs = '/i "{0}" /qn ENROLLCODE="{1}"' -f $Msi, $EnrollCode
    $Process = Start-Process -FilePath 'msiexec.exe' -ArgumentList $MsiArgs -Wait -PassThru
    if ($Process.ExitCode -notin 0, 3010) { throw "msiexec failed: $($Process.ExitCode)" }
} finally {
    Remove-Item -LiteralPath $Msi -Force -ErrorAction SilentlyContinue
}

Debian / Ubuntu

set -eu
console='https://backup.example.com:8443'
file='backupzit-agent_0.47.3_amd64.deb'
sha256='SHA256_FROM_AGENT_PACKAGES'
code='BZ1-...'
package_dir=$(mktemp -d)
trap 'rm -rf "$package_dir"' EXIT HUP INT TERM
curl --fail --silent --show-error "$console/agent/$file" --output "$package_dir/$file"
printf '%s  %s\n' "$sha256" "$package_dir/$file" | sha256sum --check --status
sudo apt-get install -y "$package_dir/$file"
sudo backupzit-agent enroll --code "$code"

console='https://backup.example.com:8443'

The Linux command backupzit-agent enroll --code is defined in cmd/backupzit-agent/service.go. The package installs its system service; enroll afterwards as root.

Agent names and removal

PATCH /api/v1/agents/1 with {"name":"Office PC"} sets the display label, trimmed to 1–255 UTF-8 bytes without control characters. GET /agents and GET /agents/{id} return it as name (falling back to the hostname). The machine's hostname, UUID, numeric ID, credentials and repo_dir are unchanged. Agent polls cannot overwrite the label. The console agent list also shows it. Naming needs the agent-management permission and writes an agent.rename audit entry.

DELETE /api/v1/agents/1 takes no body and uses the UI removal operation with backups=keep and uninstall=false. It requires the same permission, audit and four-eyes approval as UI removal: when enabled, a request is held with 409 until another user approves it in the console. The token owner cannot approve their own request. On completion the response is 200:

{"id":1,"removed":true,"backups":"kept","history":"kept","jobs":"deleted","uninstalled":false,"message":"Agent removed. Its backups stay in Activity and can be restored to another agent."}

The agent can no longer authenticate. Its job configurations are deleted, queued runs are dropped, and running/stopping runs become failed. All storage backups and completed history remain, including agents without registered repositories. Kept runs retain their IDs and have job_id:null. The software remains installed on the computer; uninstall it locally if desired. Restore retained snapshots to another active agent using the existing restore endpoint. Repeated DELETE, GET or PATCH for the removed agent returns 404. Destructive backup deletion and remote uninstallation remain UI choices.

Encrypted S3 targets

POST /api/v1/targets
{"name":"Office backups","endpoint":"s3.example.com:9000","bucket":"backups",
 "prefix":"office","region":"eu-central-1","accessKey":"...","secretKey":"...",
 "tls":true,"lockDays":30}

Returns 201 with target metadata and a generated recoveryKey. Save that key immediately; subsequent public API reads never return it or the S3 credentials. Encryption is always enabled for targets created here, and credentials use the same encryption at rest as in the console. TLS defaults to true; lockDays is 0–3650 (0 disables retention requests). Prepare the bucket and Object Lock on the storage provider before enabling it. Creation saves configuration without probing the remote service. DELETE refuses a target still used by jobs and never deletes stored backup data.

Create and change backup jobs

POST /api/v1/jobs
{"kind":"files","name":"Documents","agent_id":1,"target_id":2,
 "paths":["C:\\Users"],"excludes":["*.tmp"],"schedule":"0 22 * * *",
 "retention":{"keep_last":3,"keep_daily":7,"keep_weekly":4,"keep_monthly":12,"keep_yearly":5},
 "options":{"vss":true,"compression":"fast","limit_mbps":20}}

Returns 201 in the same shape as GET for the new job. File jobs require at least one path; image jobs require a Windows agent. An empty schedule means manual only; a five-field cron expression or an existing encoded schedule is accepted. Jobs are enabled by default. An omitted retention object defaults to 3 most recent, 7 daily, 4 weekly and 6 monthly snapshots. An explicit retention object starts with all counts at zero; zero for every rule keeps all backups. The retention rules combine, as in the UI.

POST /api/v1/jobs
{"kind":"image","name":"Windows disks","agent_id":1,"target_id":2,
 "image_disk":-1,"options":{"vss":true}}

POST /api/v1/jobs
{"kind":"image","name":"Selected disks","agent_id":1,"target_id":2,
 "options":{"image_disks":[0,2],"vss":true}}

image_disk:-1 selects all internal disks. A non-negative value selects one disk; image_partitions can narrow that single-disk choice. options.image_disks selects whole disks explicitly, read from one VSS set. VSS defaults to the agent setting (enabled on Windows); omit or set vss:null to use that default. VSS overrides, disk lists and yearly retention require the updated fork agent advertising job-options-v1 in capabilities. The fork agent sends it at enrollment and on every poll. Existing agents without this capability are rejected for these options; normal jobs remain compatible. Upgrade the agent and wait for its next poll before configuring the new options.

PATCH /api/v1/jobs/7
{"name":"Documents nightly","excludes":["*.tmp","Cache/**"],
 "retention":{"keep_daily":14},"options":{"limit_mbps":0}}

PATCH merges supplied fields, including nested options and retention. Omitted fields remain unchanged; empty lists clear selections and zero clears a numeric option. Agent, target, job kind and the original single-disk/partition selector stay fixed, as in the UI. Use the enable/disable endpoints for scheduling state. Group members must be changed through their group in the console. Only administrators may change pre/post commands and their time limit. Public job responses add raw_schedule, exclusions, retention and safe job options, while preserving the existing human-readable schedule.

Deletes and shorter retention follow the UI's four-eyes policy. When enabled, a request is recorded and the API returns 409 with instructions for a second user to decide under Approvals. A PATCH holds the shorter retention while saving its other safe changes, just as the UI does. Repeating an already pending change also returns 409. Deleting a job removes configuration and keeps its stored backups.

Browse, download and restore

File listing returns an array such as [{"name":"report.txt","path":"/C/Data/report.txt","type":"file","size":123,"modTime":"2026-11-07T10:00:00Z"}]. Paths use snapshot components and forward slashes: /C/Users on Windows or /srv/data on Linux. Use returned paths in subsequent requests; parent traversal and NUL are rejected.

Listing and downloading share the console file browser: file and Linux system backups on storage accessible from the console. Local/USB storage, expired snapshots, disk images and SSH-key-only storage retain the UI's limitations (409). A single file is streamed as application/octet-stream; folders use application/zip. A read failure after headers aborts the transfer. Treat an incomplete transfer as a failed download.

POST /api/v1/runs/123/restore
{"paths":["/C/Data/report.txt"],"target":{"directory":"C:\\Restore"}}

POST /api/v1/runs/123/restore
{"paths":["/C/Data"],"target":"original"}

Returns 202 with the newly queued run, in the GET run format. Poll it for completion. The source agent is selected by default; optional agent_id and verify match the UI choices. Use paths:["/"] for the whole backup. Restoring through an agent also works when its repository is on its local disk, since the console need not read that storage. The existing restore rules reject expired snapshots and unsupported backup types.

Page through run history

Request /api/v1/runs?limit=100, then pass the last returned id as before for the next page. Keep the same filters: for example ?agent=1&status=failed&before=456&limit=100. IDs are strictly descending, the cursor is exclusive, and new runs cannot displace older pages. An empty array ends the traversal. The response remains an array; existing job, agent, status and limit parameters remain supported. Invalid limits retain the old fallback of 100; invalid cursors return 400.

For assisted recovery store the console identity together with the numeric agent id and run id. Both are BIGSERIAL primary keys backed by noncycling sequences; ordinary inserts do not reuse deleted IDs. GET /api/v1/runs/{id} remains readable after deleting the job: job_id becomes null, while the run ID, agent ID, snapshot and repository are retained. Removing an agent through this API also keeps completed history. Explicit destructive UI deletion can remove history; UI backup adoption can move a run to a successor agent, so use the returned agent_id when resolving a saved run. IDs are scoped to the console database.

Examples

curl

curl -sk -H "Authorization: Bearer $BZ_TOKEN" https://backup.example.local:8443/api/v1/status
curl -sk -X POST -H "Authorization: Bearer $BZ_TOKEN" https://backup.example.local:8443/api/v1/jobs/7/run

PowerShell

$h = @{ Authorization = "Bearer $env:BZ_TOKEN" }
$s = Invoke-RestMethod -Uri https://backup.example.local:8443/api/v1/status -Headers $h -SkipCertificateCheck
if (-not $s.ok) { Write-Warning "BackupZit needs attention: $($s.failed_24h) failed backups" }

Use -k / -SkipCertificateCheck only with the console's self-signed certificate on a trusted network, or install the console certificate on the monitoring host.

Monitoring check

Poll /api/v1/status every few minutes and alert when ok is false. For per-job checks use /api/v1/jobs and alert when last_status is failed or last_finished is older than expected.

Jobs with an RPO also return rpo_hours, rpo_met and last_good_backup; agents return max_runs (jobs at once). The metric backupzit_job_rpo_met is 1 for a job within its RPO and 0 for one that missed it.

Prometheus and Grafana

/api/v1/metrics returns the state in the Prometheus text format: agents online, active runs, failures and warnings of the last 24 hours, suspicious backups, and per agent, job and storage target backupzit_agent_online, backupzit_job_last_status (0 success, 1 warning, 2 failed), backupzit_job_last_success_timestamp_seconds, backupzit_storage_used_bytes and backupzit_storage_free_bytes. A scrape job with a Viewer token:

- job_name: backupzit
  scheme: https
  metrics_path: /api/v1/metrics
  authorization:
    credentials: bzt_...
  static_configs:
    - targets: ['backup.example.local:8443']

Alert, for example, when time() - backupzit_job_last_success_timestamp_seconds > 2*86400 (no good backup for two days).
